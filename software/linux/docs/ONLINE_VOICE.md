# 在线语音状态

截至本发布所依据的 2026 年 10 月 11 日测试，**在线语音没有完成“讲话—识别—回答播放”的完整验证**。以下记录区分服务连接、音频上传和实际回答，不代表服务当前的实时可用性。

## 测试中观察到了什么

| 条件 | 观察结果 | 能说明什么 |
| --- | --- | --- |
| 使用所提供 Android 1.0.1 源码对应的服务配置 | WebSocket 升级与 hello 成功，取得会话和音频参数 | 客户端可以完成这套协议的连接阶段 |
| 修正主动心跳后进行真实讲话 | 上传 598 包采集音频和 20 包尾部静音；未收到识别、回答或下行音频，60 秒后客户端超时关闭 | 上传已有进展，语音往返未通过 |
| 同一协议的文字诊断 | 收到同会话回显和 `tts.start`；45 秒内没有回答、音频或 `tts.stop` | 回显不能证明麦克风 ASR，`tts.start` 不能证明合成或播放成功 |
| 改用已安装 Android 应用对应的另一服务目标 | Linux 在约 4 秒后 TCP 建连超时，尚未发送认证或 hello；主机和板端均观察到超时 | 该次失败发生在连接阶段，不能归因于 SN、认证头或 hello 字段 |

已安装 Android 应用与提供源码的版本及服务配置不同，其有限运行记录也没有成功回答。不能将两套服务的现象合并成一个已确定原因。

## 主动心跳的修正

最初的 Linux 客户端沿用 Companion 的主动 ping/pong 期限。一次上传在本地触发 `heartbeat_timeout`，记录中没有服务端 CLOSE。原 Android 连接没有配置主动 ping 间隔。

PatchX 现在默认 `voice.websocket_heartbeat=false`，不再因缺少主动 ping 对应的 pong 结束连接。它仍回复服务端 ping，并处理实际关闭、消息大小和格式限制。Companion 单独使用时仍默认开启主动心跳。

修正后，真实讲话测试没有得到识别和回复，因此心跳修正只解决了已观察到的本地主动断开问题。空闲时显示已连接也不能证明远端仍能处理请求；录音和等待回复继续受 `max_listen_s`、`response_timeout_s` 限制。

## 目前没有确定的根因

已核对的 Linux 握手包含所提供 Android 源码使用的应用设备标识，分别进入 `Device-Id` 和 `hello.device_id`。握手成功仍不能证明后端全部账号绑定和处理链路正常。

身份更新、UUID 生成方式、监听时序以及音频前处理仍存在实现差异。Linux 基础采集选择 USB 逻辑通道 0；Android 源码有 CAE 多通道处理。现有证据不足以把无回复归因于其中任何一项，也不足以判断服务端 ASR、模型或 TTS 的状态。

对另一服务目标的 TCP 超时同样没有区分出服务不可用、路由或网络过滤的具体原因。

## 使用自己的服务时

按 [开始使用](GETTING_STARTED.md#配置在线服务) 配置服务地址、设备身份及环境变量凭据。定位问题时按顺序观察：

1. TCP / TLS 能否建连。
2. WebSocket 和 hello 是否成功，是否获得有效会话及音频格式。
3. 开始讲话后是否持续上传音频。
4. 是否收到识别文字、回答内容和下行音频。
5. 下行音频是否实际从扬声器播放。

只到达前一项不能证明后一项成功。若握手和上传已经正常，仍没有识别或回答，需要服务方结合对应会话检查后端；公开反馈保留错误阶段与时间即可，不提交令牌、设备身份或录音。

## 本地音频的验证范围

有限板端记录中，USB 的 16 kHz、S16_LE、8 通道接口前四个逻辑通道有语音响应；应用选取通道 0。RK809 扬声器播放及有限 PCM 生命周期流程已有验证。这些结果分别说明采集和播放通路，不等于在线语音对话通过，也不证明八个物理麦克风、CAE、AEC 或离线唤醒能力。

板端配置见 [音频说明](../deploy/patchx/AUDIO.md)；内核驱动的验证范围见 [内核验证说明](../../../Documentation/patchx/VALIDATION.md)。
