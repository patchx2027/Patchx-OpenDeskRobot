# 在线语音状态

**2026 年 10 月 25 日，`ws://118.31.102.180:8360/` 在主机 Linux 客户端上完成了有限问答。** 文字和合成语音输入分别在同一连接中连续三轮返回正确答案、非零可解码 Opus 音频及 `tts.stop`。这次没有使用开发板的麦克风或扬声器，不能据此宣布板端完整语音对话已验收。

## 当前使用的配置

[在线模板](../deploy/patchx/live.example.json)采用成功试验的连接方式：

```text
ws://118.31.102.180:8360/?device_id=<应用SN>&user_id=<应用SN>
```

- URL 中的两个参数都使用与 `voice.device_id` 相同的应用 SN，并对参数值做 URL 编码。程序不会自动替换模板占位符。
- `voice.client_id` 使用对应服务要求的客户端标识，Bearer 令牌从 `voice.token_env` 指定的环境变量读取。
- `voice.listen_mode="realtime"`，`voice.websocket_heartbeat=false`。
- 输入为 16 kHz 单声道裸 Opus，每包 60 ms / 960 个样本；输出采样率由服务 hello 协商，本次观察到 24 kHz。不要因此将采集改成 24 kHz。

该地址是明文 `ws://`，模板显式设置 `voice.allow_insecure_ws=true`，连接中的身份、令牌和音频没有 TLS 保护。请仅使用自己获授权的服务及身份。此地址的有限验证不表示匿名开放、所有设备均可用或持续可用。配置步骤见 [开始使用](GETTING_STARTED.md#配置在线服务)。

## 10 月 25 日验证了什么

| 项目 | 结果 |
| --- | --- |
| 连接 | WebSocket 和 hello 成功，通过原 Linux 客户端严格 hello 校验 |
| 文字输入 | 同连接连续三轮，算术和首都问题得到正确回答；收到 80 个可解码音频包，无解码错误 |
| 合成语音输入 | 同连接连续三轮，均识别到对应问题并正确回答；收到 121 个可解码音频包，无解码错误 |
| 回复结束 | 各轮收到非零解码样本及 `tts.stop`，没有把固定问候或单独的 `tts.start` 算作问答成功 |

成功测试使用复用现有传输、编解码和 hello 校验代码的主机探针，并未验收完整应用状态机。探针在一次 `listen.start` 后完成同连接三轮；完整应用每次用户录音会重新发送 start，还经过自己的队列和状态机。因此模板按成功探针配置更新，完整应用的多轮操作仍需单独验收。

测试使用 C 源码对应的应用身份、Client-Id 和令牌，以及包含 `client_ip`、`device_id`、`trace_id` 的 hello。没有读取实装 Code200 应用通过板商 SDK 获取的真实序列号，也没有确认其当前动态下发的服务主机。

带上述 URL 参数的组合完成了合成语音正例。去掉两个参数后，单轮文字问答也成功；旧服务加上相同参数仍未完整回答。因此不能把 URL 参数说成服务必需条件，也不能将此前无回复仅归因于漏传参数。单次切换 `auto` 模式未得到识别或音频，不代表所有 `auto` 配置均不可用。

## 其他地址和历史问题

同日测试了源码中五个不同 WS 地址及已校验 APK 的默认地址，共六个。旧 `ws://118.196.28.154:8060/` 能握手，但合成语音上传后 20 秒内没有识别、回答或音频；文字对照只收到回显和 `tts.start`。其余四个候选未完成 WebSocket 升级，不能据此认定服务器停机或鉴权失败。

10 月 11 日的板端记录使用旧服务：心跳修正后上传了 598 包采集音频和 20 包尾静音，60 秒内没有识别和回复；文字对照 45 秒内也没有完整回答。当时换试实装 Android 应用的另一服务目标曾出现 TCP 超时。这些是不同日期、不同连接条件的历史结果，不应覆盖 10 月 25 日的成功问答记录，也不能合并为一个已确定的故障原因。

## 主动心跳的修正

最初的 Linux 客户端沿用 Companion 的主动 ping/pong 期限。一次上传在本地触发 `heartbeat_timeout`，记录中没有服务端 CLOSE；原 Android 连接没有配置主动 ping 间隔。

PatchX 默认 `voice.websocket_heartbeat=false`，避免因缺少主动 ping 对应的 pong 而结束连接。它仍回复服务端 ping，并处理实际关闭、消息大小和格式限制。Companion 单独使用时仍默认开启主动心跳。

这项修正解决了已观察到的本地主动断开，不能单独解释旧服务没有回答。空闲时显示已连接也不证明远端能处理请求；录音和等待回复仍受 `max_listen_s`、`response_timeout_s` 限制。

## 板端还需要确认什么

已有有限板端记录确认 USB 的 16 kHz、S16_LE、8 通道接口前四个逻辑通道有语音响应，应用选取通道 0；RK809 扬声器播放和有限 PCM 生命周期流程也已有验证。这些分别是采集、播放通路的结果，尚未与本次可用服务组合完成真实讲话到扬声器回答的验收。

接入时依次观察握手与音频参数、讲话上传、识别文字、回答内容、下行音频及实际播放。服务端问题需要结合对应会话排查，公开反馈不要包含令牌、设备身份或录音。

Linux 基础路径没有复现原 Android 的 CAE、阵列 AEC 或离线唤醒。设备绑定、摄像头问答、全部模型和工具以及长时间稳定性也不在这次有限验证范围内。板端配置见 [音频说明](../deploy/patchx/AUDIO.md)，内核驱动范围见 [内核验证说明](../../../Documentation/patchx/VALIDATION.md)。
